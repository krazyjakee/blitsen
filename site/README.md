# The documentation site

The GitHub Pages site at <https://blitsen.dev/>. Plain static HTML and one
stylesheet, generated by a bun script with no dependencies.

```sh
bun run site:build     # build to site/dist with the root base path
bun run site:check     # dead links, missing anchors, unrendered markdown
bun run site:serve     # build and serve it locally
```

`site/dist` is generated and gitignored. Deployment is
[`.github/workflows/pages.yml`](../.github/workflows/pages.yml), which builds on
pushes to `main` that touch `docs/`, `site/` or `assets/brand/` and uploads a Pages
artifact — nothing is committed back to the repository.

**One-time setup:** Settings → Pages → Source must be set to *GitHub Actions*.

## The one rule

**Documentation pages are generated from `docs/*.md`. Do not transcribe prose into
this directory.**

The compatibility profile is generated from the runtime itself. A hand-copied site
would quietly become a second, wrong source of truth the first time it changed. If a
docs page needs different words, change the markdown.

The single exception is the home page, [`build/landing.ts`](build/landing.ts), which
is hand-authored as a short route into the task-based guides.

## Adding a page

Add the file to `docs/`, then add an entry to the relevant user-task group in
[`build/content.ts`](build/content.ts) with its slug, nav label, title and one-line
blurb. Nothing else needs touching — the sidebar, the documentation index, the home
page card grid and the sitemap are all derived from that registry.

Contributor specifications, historical decisions and milestone records belong in
`INTERNAL_PAGES`. They are still built so existing links work, but are deliberately
absent from the user navigation and sitemap.

## Layout

| File | Responsibility |
| --- | --- |
| `build/main.ts` | Orchestration: read, render, write, copy assets, emit sitemap. |
| `build/content.ts` | The page registry, and the rules for rewriting repo links. |
| `build/markdown.ts` | Markdown → HTML for exactly the syntax the corpus uses. |
| `build/layout.ts` | Page shell: head, masthead, sidebar, table of contents, footer. |
| `build/landing.ts` | The hand-authored home page. |
| `build/check.ts` | Post-build verification. |
| `assets/site.css` | The whole stylesheet. |

## Link rewriting

Markdown in `docs/` is written to be read on GitHub, so its links point at repository
paths. `rewriteDocLink` resolves them for the site:

- a sibling `*.md` that has a registered page → that page's URL
- an image → the site's own `assets/` copy
- anything else in the tree (`examples/`, `packages/`, `spikes/`) → a GitHub blob link

Heading anchors use GitHub's slug algorithm, so cross-document links written for
GitHub — `COMPATIBILITY.md#native-modules` — keep working here without editing.

## Design

The palette and type pairing come from [`docs/product.html`](../docs/product.html):
paper and ink, an ultramarine accent, a serif reading measure with mono display type.
Dark mode follows `prefers-color-scheme` and can be overridden by a toggle that
persists to `localStorage`.

The crest is the rampant reindeer from [`assets/brand`](../assets/brand), inlined into
the markup so it takes the surrounding ink colour rather than needing a second file
for dark mode.

## What it does not have

No client-side JavaScript beyond a theme toggle and the mobile nav — no search index,
no hydration, no analytics. Search is the browser's find-in-page, which works because
each document is one page rather than many fragments. If full-text search is wanted
later it should be a build-time index, not a runtime dependency.
